# Release Testing — Templates

Verbatim templates for the `release-testing` skill. Open this when you first post results (Step 3e)
and when creating the artifact (Step 6).

## Linear QA-comment body (Step 3e)

One consolidated comment per Linear ticket, edited in place. **Keep the exact header
`### Product Review / QA Test Results` and the `**Changelog summary**` line** — `release-changelog`
greps for both. One results-table row per acceptance check.

```
### Product Review / QA Test Results

**Changelog summary**
<changelog line from 3d>

**Scope**
- PR: #<number>
- Environment: <preview / staging URL>
- Tested as: <user(s), e.g. "site.admin"; note impersonation for permission checks>
- Status: <in progress / testing complete>

**Results**

| Check | Result |
|---|---|
| **A1** <short desc> | ✅ PASS |
| ... | ⚠️ ... / ❌ FAIL |

**Acceptance-criteria coverage:** <map the checks back to the ticket's numbered criteria>

---

### 🐞 Issues
<one self-contained block per bug — surface/file, numbered repro, expected vs actual, evidence
link (screenshot/video), and a live status: OPEN / ✅ FIXED & re-verified. Omit the section if none.>

---

**Result:** <PASS / FAIL / PARTIAL / PENDING-HUMAN>
<brief summary>

---
*Generated by Claude Code QA skill · <date>*
```

## `QA-RESULTS.md` skeleton (Step 6)

```markdown
# RC QA Results — <date>

## Results

| # | PR | Type | Problem | Solution | Area | Result | Notes |

## Human-verify checklist

### #<n> — <title> (<TICKET>)
**Precondition:** <data/setup needed>
1. <step>
2. <step>

- **Fail =** <observable failure>

## Slack block

:white_check_mark: <PR title> (#<n>)
:x: <PR title> (#<n>) — <short reason>

\`\`\`
```
